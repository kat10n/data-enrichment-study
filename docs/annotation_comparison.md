# Сравнение разметок A и B

Скрипт сопоставляет ваши экспорты Label Studio по `data.sample_id`, считает согласованность и составляет список для совместного разбора. Он не выбирает правильный ответ вместо аннотаторов и не меняет исходные файлы.

## Запуск

Нужен Python 3.9 или новее. Дополнительные библиотеки, Label Studio и доступ к интернету для расчёта не нужны.

Из корня репозитория:

```bash
python3 scripts/compare_annotations.py
```

В Windows можно использовать `py -3 scripts/compare_annotations.py`.

По умолчанию читаются:

- `data/annotated_data/telegram/text_A.json` и `text_B.json`;
- `data/annotated_data/photo/images_A.json` и `animals_B.json`;
- `data/annotated_data/photo/original_exports/images_A_2026-11-17.json` — сохранённый исходный экспорт A до изменения `IMG021` с `animal` на `empty`.

Результаты появятся в `artifacts/annotation_comparison/`:

| Файл | Для чего нужен |
| --- | --- |
| `REPORT.txt` | Краткие результаты, покрытие, коэффициенты и дальнейшие действия |
| `review_list.txt` | ID спорных объектов, ответы A/B и причины проверки |
| `comparison.json` | Все пары, таблицы сопряжённости, рамки, IoU, время и контрольные суммы входных файлов |
| `adjudication_template.json` | Пустой шаблон для совместных итоговых решений |

**При повторном запуске существующий `adjudication_template.json` сохраняется.** Остальные отчёты пересчитываются. Для новой версии входных файлов используйте новую папку, чтобы старые решения не смешались с новым сравнением:

```bash
python3 scripts/compare_annotations.py --output-dir artifacts/annotation_comparison_v2
```

Пути к экспортам можно переопределить: `--text-a`, `--text-b`, `--images-a`, `--images-b`, `--images-a-original`. Полный список: `python3 scripts/compare_annotations.py --help`.

## Что считается автоматически

1. Проверяется уникальность ID, одинаковый состав и содержимое заданий, одна сохранённая аннотация на задание. При несовместимых входах скрипт останавливается с ошибкой, вместо незаметного сравнения разных выборок.
2. Для текстов и наличия животных считаются доля совпадений, Cohen’s kappa и таблица A/B. `needs_review` и `excluded` не считаются бинарными классами: такие пары показываются отдельно, вместе с покрытием. Если kappa математически не определена, сохраняется `null`.
3. Рамки сопоставляются один к одному при **IoU ≥ 0.50**. Сначала максимизируется число допустимых пар, затем сумма IoU. Используется алгоритм минимальной стоимости максимального потока, а не жадный выбор ближайшей рамки.
4. Сохраняются количество рамок A/B, число совпавших пар, несопоставленные рамки, средняя и медианная IoU, `F1 = 2M / (N_A + N_B)`. Кадры с небинарным статусом исключаются из этой метрики и остаются в списке разбора. Два пустых набора рамок не получают искусственный IoU или F1, равный единице.
5. Для геометрии используются проценты от одного и того же изображения; это даёт тот же IoU, что пиксели. Размеры исходного изображения сверяются между аннотациями. Самих изображений скрипт не скачивает и не проверяет визуально.
6. В список попадают разные метки, нерешённые статусы, несопоставленные рамки, низкая уверенность, отсутствующие пояснения и разные `occluded`/`truncated`. Пары с IoU ниже 0.75 дополнительно предлагаются для просмотра. Последнее — подсказка, а не требование, чтобы каждая рамка обязательно превышала 0.75; ориентир кодбука относится к медиане.
7. Время берётся из `annotations[].lead_time`. Это время счётчика Label Studio, которое может включать паузы. Пропуски и нули показываются отдельно; ручное активное время не придумывается.

Метрики для **исходного A** и для **текущего A после исправления** приведены раздельно. Для описания первоначальной согласованности используйте исходный экспорт. Не заменяйте её «согласованностью» после совместного обсуждения.

## Что делаете вручную

Откройте `review_list.txt`. Сначала разберите объекты с очередью `first`, затем `followup`.

Для каждого ID откройте сообщение или фотографию в своих проектах, сравните ответы и рамки, сверяйтесь с кодбуком. Запишите согласованную метку/рамки и короткую причину. При невозможности уверенно решить оставьте `unresolved`; такой пример пока не включается в обучение.

В шаблоне итогов предусмотрены поля `final_status`, `final_label`, `final_boxes`, `resolution_reason`, `resolved_by`, `resolved_at`, `codebook_version`. До обсуждения они остаются пустыми. Для `final_status` допустимы `accepted`, `excluded`, `unresolved`; время и участников указывайте фактические. Итоговые рамки записываются в процентах с размерами исходного изображения, как в экспорте. Исходные A/B не перезаписывайте.

После разбора отдельно формируется итоговый набор данных. Скрипт сравнения сам этого не делает: совпадение двух ответов ещё не гарантирует их правильность.

## Особенности этой коллекции

- Часть решений A по фотографиям обсуждалась с ИИ. Нельзя описывать весь процесс как полностью самостоятельную разметку без подсказок.
- Отдельный завершённый пилот и утверждённая после него версия кодбука 1.0 не подтверждены. Этот расчёт сравнивает фактически полученные экспорты; он не заменяет пилот задним числом.
- Метрики отражают согласованность аннотаций, а не качество обученной модели.

## Проверка скрипта

```bash
python3 -m unittest discover -s scripts -p 'test_compare_annotations.py' -v
```

Тесты проверяют kappa и покрытие, пустые кадры, порог IoU, приоритет количества пар, соответствие алгоритма полному перебору на небольших матрицах, исходную/исправленную версии A и сохранность введённых человеком итоговых решений.
